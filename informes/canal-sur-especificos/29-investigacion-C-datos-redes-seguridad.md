### 12.2 DQL y la clasificación de sentencias

- **DQL no es una categoría del estándar ni de Oracle.** Oracle (Fuente D: «Types of SQL Statements», https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Types-of-SQL-Statements.html, leída 05-10-2026) divide en: «Data Definition Language (DDL) Statements Data Manipulation Language (DML) Statements Transaction Control Statements Session Control Statements System Control Statements Embedded SQL Statements».
- Oracle mete GRANT/REVOKE en DDL (no en un DCL aparte): DDL permite «Create, alter, and drop schema objects Grant and revoke privileges and roles Analyze information on a table, index, or cluster Establish auditing options Add comments to the data dictionary». «The database implicitly commits the current transaction before and after every DDL statement.»
- DML Oracle: «Data manipulation language (DML) statements access and manipulate data in existing schema objects. These statements do not implicitly commit the current transaction. The data manipulation language statements are: CALL DELETE EXPLAIN PLAN INSERT LOCK TABLE MERGE SELECT UPDATE»
- **La frase que justifica separar DQL**: «The SELECT statement is a limited form of DML statement in that it can only access data in the database. It cannot manipulate data stored in the database, although it can manipulate the accessed data before returning the results of the query.»
- TCL Oracle: «Transaction control statements manage changes made by DML statements. The transaction control statements are: COMMIT ROLLBACK SAVEPOINT SET TRANSACTION SET CONSTRAINT»
- Recomendación al redactor: presentar DQL (SELECT) como la clasificación didáctica que usa el enunciado, decir que hay fabricantes que la incluyen en DML (cita de Oracle) y que GRANT/REVOKE (DCL en la clasificación didáctica) Oracle los pone en DDL. Esto también corrige el tono absoluto de RTVE («SELECT ... son las sentencias básicas del DML»): no es falso, pero el enunciado de Canal Sur separa DQL.
- No confirmado: que ISO/IEC 9075 use los nombres «DDL/DML/DQL»; no se pudo leer la norma (de pago). Lo de la clasificación interna del estándar (SQL-schema statements, SQL-data statements…) se recuerda pero **no se ha leído**: no usarlo.

### 15.1 El fundamento legal: Ley 40/2015, arts. 155 a 158

### 13.1 Cabecera IPv4 — RFC 791 (septiembre de 1981)

- Figura 4, «Example Internet Datagram Header», campos en este orden: «Version | IHL | Type of Service | Total Length / Identification | Flags | Fragment Offset / Time to Live | Protocol | Header Checksum / Source Address / Destination Address / Options | Padding».
- «IHL: 4 bits — Internet Header Length is the length of the internet header in 32 bit words, and thus points to the beginning of the data. Note that the minimum value for a correct header is 5.» (5 × 32 bits = 20 octetos de cabecera mínima: cálculo del redactor, se puede decir).
- «Time to Live: 8 bits — This field indicates the maximum time the datagram is allowed to remain in the internet system. If this field contains the value zero, then the datagram must be destroyed.»
- «Header Checksum: 16 bits — A checksum on the header only. Since some header fields change (e.g., time to live), this is recomputed and verified at each point that the internet header is processed.»
- **Salvedad**: el campo «Type of Service» fue redefinido después (campo DS/ECN, RFC 2474 y 3168); **no leídos**: si el redactor lo menciona, que diga sólo que RFC 791 lo llama así.

### 13.2 Cabecera IPv6 — RFC 8200 (julio de 2017, «STD: 86», «Obsoletes: 2460»)

- Sección 3: campos «Version | Traffic Class | Flow Label / Payload Length | Next Header | Hop Limit / Source Address / Destination Address».
  - «Version 4-bit Internet Protocol version number = 6.» «Traffic Class 8-bit Traffic Class field.» «Flow Label 20-bit flow label.»
  - «Payload Length 16-bit unsigned integer. Length of the IPv6 payload, i.e., the rest of the packet following this IPv6 header, in octets. (Note that any extension headers (see Section 4) present are considered part of the payload, i.e., included in the length count.)»
  - «Next Header 8-bit selector. Identifies the type of header immediately following the IPv6 header. Uses the same values as the IPv4 Protocol field».
  - «Hop Limit 8-bit unsigned integer. Decremented by 1 by each node that forwards the packet. When forwarding, the packet is discarded if Hop Limit was zero when received or is decremented to zero.»
  - «Source Address 128-bit address of the originator of the packet.» «Destination Address 128-bit address of the intended recipient of the packet (possibly not the ultimate recipient, if a Routing header is present).»
- Sección 4: «In IPv6, optional internet-layer information is encoded in separate headers that may be placed between the IPv6 header and the upper-layer header in a packet.» Orden recomendado: «IPv6 header / Hop-by-Hop Options header / Destination Options header (note 1) / Routing header / Fragment header / Authentication header (note 2) / Encapsulating Security Payload header (note 2) / Destination Options header (note 3) / Upper-Layer header».
- Fragmentación: «fragmentation in IPv6 is performed only by source nodes, not by routers along a packet's delivery path» (contraste con IPv4). «The Fragment header is identified by a Next Header value of 44».
- Sección 5: «IPv6 requires that every link in the Internet have an MTU of 1280 octets or greater. This is known as the IPv6 minimum link MTU.» «It is strongly recommended that IPv6 nodes implement Path MTU Discovery [RFC8201]».
- Diferencia con IPv4 que se ve en las dos figuras: IPv6 no tiene campo de suma de comprobación de cabecera ni IHL (la cabecera tiene longitud fija). Es lectura directa de las figuras; la cifra «40 octetos» de cabecera fija **no** aparece literal en lo leído (se deduce: 4+4+16+16 = 40 bytes). El redactor puede darla como cálculo.

### 13.3 Direccionamiento IPv6 — RFC 4291 (febrero de 2006), RFC 4193, RFC 5952

- RFC 4291, 2: «IPv6 addresses are 128-bit identifiers for interfaces and sets of interfaces». «There are three types of addresses: Unicast: An identifier for a single interface. (…) Anycast: An identifier for a set of interfaces (typically belonging to different nodes). A packet sent to an anycast address is delivered to one of the interfaces identified by that address (the "nearest" one, according to the routing protocols' measure of distance). Multicast: An identifier for a set of interfaces (…) delivered to all interfaces identified by that address.» «There are no broadcast addresses in IPv6, their function being superseded by multicast addresses.»
- 2.2 notación: «The preferred form is x:x:x:x:x:x:x:x, where the 'x's are one to four hexadecimal digits of the eight 16-bit pieces of the address.» «The use of "::" indicates one or more groups of 16 bits of zeros. The "::" can only appear once in an address.» Ejemplos: «2001:DB8:0:0:8:800:200C:417A» → «2001:DB8::8:800:200C:417A»; «0:0:0:0:0:0:0:1» → «::1» (loopback); «::» (unspecified). Forma mixta: «x:x:x:x:x:x:d.d.d.d», ejemplos «0:0:0:0:0:FFFF:129.144.52.38», comprimido «::FFFF:129.144.52.38» (comprobado en el RFC).
- 2.4, tabla: «Unspecified 00...0 (128 bits) ::/128»; «Loopback 00...1 (128 bits) ::1/128»; «Multicast 11111111 FF00::/8»; «Link-Local unicast 1111111010 FE80::/10»; «Global Unicast (everything else)». «Anycast addresses are taken from the unicast address spaces (of any scope) and are not syntactically distinguishable from unicast addresses.»
- RFC 4193 (direcciones locales únicas, equivalente funcional de las privadas): «This document defines an IPv6 unicast address format that is globally unique and is intended for local communications, usually inside of a site. These addresses are not expected to be routable on the global Internet.» Formato: «| 7 bits |1| 40 bits | 16 bits | 64 bits | Prefix |L| Global ID | Subnet ID | Interface ID |», «Prefix FC00::/7 prefix to identify Local IPv6 unicast».
- RFC 5952 (representación recomendada): 4.2.1 «The use of the symbol "::" MUST be used to its maximum capability. For example, 2001:db8:0:0:0:0:2:1 must be shortened to 2001:db8::2:1.» 4.2.2 «The symbol "::" MUST NOT be used to shorten just one 16-bit 0 field.» 4.3 «The characters "a", "b", "c", "d", "e", and "f" in an IPv6 address MUST be represented in lowercase.» (Ojo: RFC 4291 escribe en mayúsculas; las dos formas son válidas al leer, RFC 5952 fija cómo escribir.)

### 13.4 Convivencia y transición IPv4/IPv6

- RFC 4213 (Abstract): «This document specifies IPv4 compatibility mechanisms that can be implemented by IPv6 hosts and routers. Two mechanisms are specified, dual stack and configured tunneling. Dual stack implies providing complete implementations of both versions of the Internet Protocol (IPv4 and IPv6), and configured tunneling provides a means to carry IPv6 packets over unmodified IPv4 routing infrastructures.» «This document obsoletes RFC 2893.» Sección 2: «IPv6 nodes that provide complete IPv4 and IPv6 implementations are called "IPv6/IPv4 nodes".»
- RFC 6146 (Abstract), traducción: «This document describes stateful NAT64 translation, which allows IPv6-only clients to contact IPv4 servers using unicast UDP, TCP, or ICMP. One or more public IPv4 addresses assigned to a NAT64 translator are shared among several IPv6-only clients. When stateful NAT64 is used in conjunction with DNS64, no changes are usually required in the IPv6 client or the IPv4 server.»
